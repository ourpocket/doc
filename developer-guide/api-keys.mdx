---
title: "API keys"
description: "Create, rotate, and revoke environment-scoped project credentials."
---

Creating a project returns its first Sandbox key once. The key begins `op_test_sk_`. Use it on your server with `Authorization: Bearer <key>` or `x-api-key: <key>` for normalized `/v1` financial operations.

Create a Production key with `POST /v1/projects/{projectId}/api-keys`, a user JWT, and `{ "scope": "live" }`. A live key begins `op_live_sk_`. A project can have one key per scope; rotate an existing key rather than creating another with the same scope. Create and rotate responses include the raw key once. `GET /v1/projects/{projectId}/api-keys` returns masked metadata, never the raw secret. `POST /v1/projects/{projectId}/api-keys/{id}/rotate` revokes the old key and returns a replacement. `DELETE /v1/projects/{projectId}/api-keys/{id}` revokes it.

The key scope determines environment. A test key cannot read a live payment even when both belong to the same project. Project quotas and revocation are checked on runtime requests. Keep keys in server-side secret storage and use separate key values per environment.

Every financial creation requires an `Idempotency-Key` of up to 200 characters. Reusing the same key with the same operation and body returns the original resource. Reusing it with a different request returns `409 Conflict`. After a timeout, reuse the **same** key and body and inspect the original operation; do not create another financial write with a new key. Pass a UUID `X-Request-Id` when you want to correlate logs and events.
