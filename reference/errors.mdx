---
title: "Errors and uncertain outcomes"
description: "Handle validation, conflicts, provider uncertainty, and SDK errors."
---

The backend uses HTTP status codes and Nest error responses. It does not expose a single stable enum of provider-specific error codes. Read the HTTP status, message, and `X-Request-Id`; do not branch on an invented code string.

| Status | Typical cause | What to do |
| --- | --- | --- |
| `400` | Invalid payload, missing idempotency key, unavailable provider capability, ambiguous provider choice, or unsupported environment operation | Correct the request or select an eligible connection |
| `401` | Invalid, revoked, expired, or exhausted key | Use an active key for the intended project and environment |
| `404` | Resource or connection not found in this scope | Check the UUID, project, and environment |
| `409` | Idempotency key reused with a different body, amount/reference mismatch, or unsafe refund state | Inspect the original operation before changing anything |
| `502` | Malformed provider response or a wallet provider request error | Inspect the operation and logs; do not blindly repeat a financial write |

A transport timeout or uncertain provider response can leave the **resource** with `status: "unknown"` even when the create request itself returned successfully. This is deliberate: the provider may have accepted the write. Reuse the same idempotency key and body to retrieve it. For Production payments and refunds, verify or run reconciliation against the original provider; a later terminal state must not be overwritten by an old webhook.

The TypeScript SDK throws `OurPocketError` with `status` and `requestId`. A client-side network failure has `status: 0`. Keep the idempotency key and investigate; the SDK never automatically retries writes.
