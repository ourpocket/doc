---
title: "Authentication"
description: "Use a user JWT for management and a project key for runtime operations."
---

OurPocket uses separate credentials for management, financial operations, provider connections, and outbound webhooks.

| Credential | Purpose | Where to send it |
| --- | --- | --- |
| User JWT | Project, provider, key, webhook, and dashboard management | `Authorization: Bearer <jwt>` |
| `op_test_sk_` or `op_live_sk_` key | Runtime `/v1` financial APIs | `Authorization: Bearer <key>` or `x-api-key` |
| Provider credentials | Your Production connection | Dashboard provider connection form; never in a payment or wallet body |
| `whsec_` secret | Verify outbound events at your endpoint | Keep on your webhook receiver |

`POST /v1/auth/login` returns a user JWT. Create a project with that JWT, then store the one-time Sandbox key from the project response. Generate a Production key under the project's **API keys** when you are ready to connect real providers. Key listings show masked metadata; a rotation returns its replacement once. A revoked key cannot access runtime operations.

The runtime key determines both project and environment. Send an optional UUID `X-Request-Id` to correlate operations, events, deliveries, and logs. Never put a secret key in browser code or include provider credentials in a financial request body.

Read [API keys](/developer-guide/api-keys) and [webhook signatures](/user-guide/webhooks) for the full lifecycle.
