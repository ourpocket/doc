---
title: "Sandbox and Production"
description: "Understand project environments and their isolated resources."
---

Each project has a Sandbox and a Production environment. The key determines the project and environment for runtime `/v1` requests; you cannot override it with a request body or dashboard header.

| | Sandbox | Production |
| --- | --- | --- |
| Key prefix | `op_test_sk_` | `op_live_sk_` |
| Provider credentials | Not needed | Your connected provider accounts |
| Payments and refunds | Simulated | Paystack or Flutterwave hosted checkout and refunds |
| Wallets | Simulated fiat balances | Turnkey or Privy chain address creation |
| Funding, debit, internal transfer | Simulated | Unavailable |
| Events, webhooks, logs | Environment-scoped | Environment-scoped |

Sandbox supports explicit `success`, `failure`, `pending`, `insufficient_funds`, `timeout`, and `provider_outage` scenarios where the operation accepts a scenario. Pending operations can be completed or failed with `POST /v1/sandbox/operations/{id}/complete`. Timeout and outage scenarios are represented as `unknown`; they do not call an external provider.

Production rejects simulation scenarios and fake funding. A hosted checkout starts `pending`, not completed; verify it against the original provider before treating it as settled. A provider timeout can leave an `unknown` operation. Inspect or reconcile that operation rather than starting another write with a different key.

The dashboard selector changes its management requests with `X-Environment: sandbox` or `production`. It does not alter what a project API key can access. Historical records without a provable environment are excluded from the normalized financial API.
