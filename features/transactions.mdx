---
title: "Transactions and inspection"
description: "Understand normalized resources, events, and API logs."
---

A Payment is a hosted-checkout operation. A Refund reverses some or all of a completed Payment. A Sandbox Transfer moves simulated fiat funds between wallets. `GET /v1/financial-transactions` lists these normalized financial records together; it does not initiate money movement.

Each resource includes a UUID `id`, `projectId`, `environment`, `kind`, `status`, `amount` where relevant, `currency` where relevant, `provider`, `providerReference`, `parentId`, `details`, `requestId`, and timestamps. Amounts are integer minor-unit strings. Production chain wallets have `currency: null` and `details.balance: null`.

Statuses are `pending`, `unknown`, `completed`, and `failed`. `pending` means more provider or simulation work is needed. `unknown` means the outcome is uncertain; it is never permission to repeat a financial write automatically. The `details.routingDecision` on a routed payment records the selected provider, candidates, health snapshot, policy, and reason.

`GET /v1/events` lists normalized lifecycle events. `GET /v1/api-logs` lists redacted application and provider operation logs. Both are project/environment scoped and return up to the latest 100 entries. Logs expire after seven days; financial resources and delivery metadata are retained. Use the shared request ID to follow an operation into its event and webhook delivery.

In the dashboard, **Payments** shows checkout links and refunds; **Transactions** is a read-only history; **API Logs** opens a detail panel for inspection. The older `/v1/transactions` and `/v1/wallets/*` routes are compatibility APIs with different semantics. New integrations should use the normalized endpoints in [the API reference](/reference/endpoints).
